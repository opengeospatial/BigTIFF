I.  Abstract

This document is OGC Standard that describes an extended internal structure for an image file that requires more than 4 Gibibytes (232). The general structure is similar to the TIFF specification version 6 but it replaces two essential data structures called Image File Header and Image File Directory for new ones that support the necessary longer integer numbers that acts as internal offsets of the file. It also adds 3 new data types for very long integers. It is expected that other OGC standards, such as GeoTIFF, Will depend on this OGC Standard in the near future.

III.  Preface

When the TIFF format was defined back in 1986 the storage capacity of the computers made difficult (or even impossible) for an single file image to be bigger than Gibibytes (232) long. But today capacities makes it viable and if the file can be random accessed in small pieces, could be useful for example in the case of a big remote sensing dataset that is delivered in a single TIFF file.

The basic BigTIFF design was first proposed in 2004 and refined in (this discussion (now only accessible in the web.archive.org) on the Aware Systems (Aware Systems mailing list (now only available in the web.archive.org). Contributors to the design discussion included Lynn Quam, Frank Warmerdam, Chris Cox, Rob Tillaart, Dan Smith, Bob Freisenhahn, Andrey Kiselev, Phillip Crews, and Gerben Vos. The authors thank all those who came before them for creating libtiff and designing the BigTIFF enhancements. The BigTIFF format was proposed in https://www.awaresystems.be/imaging/tiff/bigtiff.html, maintained by Joris Van Damme, and has been stable in recent years (now only accessible in the web.archive.org).

Changes were made by Ole Eichhorn (ole.eichhorn@gmail.com) while at (www.aperio.com)[Aperio] (now only accessible in the web.archive.org) and the work was donated as public domain, in gratitude to Sam Leffler, Silicon Graphics, Joris Van Damme, Aware Systems, Frank Warmerdam, Andrey Kisley, Mike Welles, and all who have worked on libtiff over the years to provide support to files bigger than previous limitations. These changes were published on an “as is” basis and neither Ole Eichhorn nor Aperio made any warranty as to their fitness for any intended use.

The intention of this Standard is to elevate the work done by all cited previous people to the category of International Standard recognizing and respecting their work. This document is an adaptation of the https://www.awaresystems.be/imaging/tiff/bigtiff.html specification to an OGC Standard format following the OGC Modular Specification. It was done with the intention of creating a transcription with no practical modifications, so old BigTIFF implementations would be immediately compatible with this Standard. In the process, the Standard was made partially dependent from the classical TIFF v6 specification. It is expected that next versions of GeoTIFF will support both classical TIFF v6 and BigTIFF overcoming file size limitations.

IV.  Security considerations

While this Standard upgrades TIFF by accommodating capacity for massive datasets (such as satellite imagery, gigapixel medical pathology slides, and high-fidelity 3D maps) it introduces specific, security vulnerabilities. The following list is not exhaustive but highlights the most critical concerns:

Memory Allocation Bombs (Severe DoS): With BigTIFF’s 64-bit fields, a malicious actor can craft an Image File Directory (IFD) tag indicating that an array requires exabytes or petabytes of memory. If a parser software naively executes memory allocation (malloc) based on that 64-bit header value before validating the actual file payload size, it will cause an immediate application crash or severe system-wide memory exhaustion.

64-bit to 32-bit Truncation Vulnerabilities: Legacy applications handle file pathways using 32-bit code. When a modern BigTIFF library passes a 64-bit offset or byte-count pointer to an older code, the upper bits can be truncated. This type mismatch creates scenarios leading to out-of-bounds memory reads or heap corruptions.

Unchecked Malware Staging & Steganography: Because BigTIFF files easily scale into tens of gigabytes, they are perfect vehicles for data exfiltration or malware storage. Most enterprise antivirus software, firewalls, and email scanners bypass deep content scanning for files exceeding 50 MB to 100 MB to maintain performance. Attackers can embed entire encrypted payloads into obscure 64-bit tag blocks without altering the viewable image, completely avoiding detection.

Infinite Tiles: BigTIFF heavily relies on tiled structures to read giant images efficiently. A corrupted or malicious file can define millions of deeply nested that may lock up server CPU threads almost indefinitely.

1.  Scope

This document is OGC Standard that describes an extended internal structure for a image file that requires more than 4 Gibibytes (232). The general structure is similar to the TIFF specification version 6 but two essential data structures called Image File Header and Image File Directory are replaced by Big File Header and Big Image File Directory to support the necessary longer integer numbers that act as internal offsets of the file. It also adds 3 new extra data types: LONG8 (uint64) SLONG8 (int64) or IFD8 (uint64).

The intention of this Standard is to elevate the work done by the original creators of BigTIFF to the category of International Standard recognizing and respecting their work. Introducing changes in the original work is out of scope of this Standard version.

NOTE:  In this Standard Gibibytes (232) is used instead of the most common Gigabytes (109) because the limit in the file format size is related to internal offsets expressed using 32 bit long integer numbers.

7.  Overview

7.1.  What is BigTIFF

The TIFF file format was defined in mid-1980s as an extensible format. At that time 32bit offsets seemed sufficient, giving a limit to a 4 Gibibytes (232) file size. This has been quite sufficient for many years. Today however, there is a need for a good multi-purpose open image file format that can handle huge images, or very large collections of images, that together exceed the 4 Gibibytes (232) boundary.

BigTIFF is very similar to the original TIFF and only changes some internal headers to support 64 bits offsets and data types. The benefits of BigTIFF closely resembling TIFF are huge. For instance, existing TIFF libraries can quite easily extend their support for TIFF to also include this variant. This results in a very short list of requirements. All the much-appreciated properties of the TIFF format that have been around and have been extended for decades are inherited. All properly known tags are being reused, all supported bit depths and datatypes remain valid. The arbitrary number of ‘extra channels’, the tiling and striping schemes, the multitude of compression schemes, and the private tag scheme, that made TIFF very useful in pre-press as well as for storing scientific data, and many other applications, all remain intact. Yet, by changing the offset bit depth, BigTIFF files are no longer restrained by the 4 Gibibytes (232) limitation from which classic TIFF suffers.

Since the BigTIFF format is based on the TIFF format, the reader is encouraged to familiarize with the current version of the TIFF specification before reading this.

7.2.  Origin and compatibility

This Standard collects the attempt to launch a new variant of TIFF, called BigTIFF, that closely resembles TIFF, but uses 64bit offsets instead. The results of the BigTIFF discussion resulted in an original specification exposed in the Aware Systems website: https://web.archive.org/web/20240706160214/https://www.awaresystems.be/imaging/tiff/bigtiff.html. Aware Systems was managed by Joris Van Damme but was discontinued after July 6th, 2025 and can only be accessible in backup copies done by the WebAchive iniciative. In order to preserve and consolidate the BigTIFF iniciative, the process of creating this Standard started with Joris Van Damme initial work and was translated it into an OGC standard. Another source of information on the BigTIFF format is the BigTIFF design page at the LibTiff site http://bigtiff.org/.

There are at least two independent implementations of the original BigTIFF specification. (AWare Systems AsTiff, and LibTiff since version 4.0). This OGC Standard does not contradicts the original BigTIFF specification so the implementations of BigTIFF are immediatelly compatible with this Standard.

7.4.  Implications for EXIF

EXIF is a metadata standard that uses a TIFF-compatible structure such as image file header and image file directory as a container. It adopts many of the accepted TIFF Revision 6.0 Final tags and provides an extra list of EXIF tags and a pointer to a dedicated EXIF sub-IFD.

EXIF extra tags define a photography-focused subset and extends it with standardized metadata fields for digital cameras. It captures information such as exposure, date/time, GPS, and thumbnail-related data. For TIFF files, EXIF information is integrated by adding new TIFF tags. For the JPEG format, EXIF is included in the Application Market Segment (APP1). APP1 is recorded immediately after the SOI marker indicating the beginning of the file.

EXIF specification references Classic TIFF as a data structure and current cameras are not generating images with size bigger that 4Gib. However, nothing prevents a BigTIFF file to use EXIF following the same pattern specified in this Standard (by replacing IFH and IFDs with BIFH and BIFDs respectively). Implementations of EXIF readers should consider the possibility to find BigTIFF structures when reading EXIF, and the need to transform them to Classic TIFF structures when exporting data and metadata to JPEG or other formats.

NOTE:  In the future, the structure BigTIFF format could support both IFDs and BIFDs and by saving this EXIF part in the first part of the document this issue could be avoided. However introducing changes in the original BigTIFF specification is out of scope of this Standard.

8.  BigTIFF requirements

The BigTIFF standard provides a solution for a TIFF file that requires a file size larger than 4 Gibibytes (232). In a BigTIFF file, the largest possible file is 264 bytes in length. In this situation the classic TIFF internal 32 bit offsets are not long enough to point to the a byte beyond the 4 Gibibytes limit.

8.1.1.  Basic format

Requirement 1

Identifier/req/core/big-offsets
Included inRequirements class 1: https://www.opengis.net/spec/BigTIFF/1.0/req/core
A

A BigTIFF SHALL shall be a file with a size bigger than 4Gibibytes or a TIFF file using using the new data types defined in this Standard

B

A BigTIFF SHALL begin with a 16 byte big image file header (that replaces the TIFF Revision 6.0 Final 8 byte image file header)

C

A big image file header SHALL point to the first big image file directory (BIFD). A big image file directory contains information about the image, as well as pointers to the actual image data in a similar way as a image file directory does in TIFF Revision 6.0 Final

NOTE 1:  There is a paradox in the actual 4 Gibibytes limit. In a case that all Image File Directories are at the beginning of the file, a 32 bit offset can be sufficient to point to an array of image strips offsets (Tag code 273) and 32 bit numbers may be sufficient for image strips offsets, but imagining that strips are in other and that the second to last strip is at the offset 4.1 109 and that the last strip is 250 MegaByte long, the total size of the file will cross the 4 GiB boundary. In a case like this, even if BigTIFF it is not technically necessary, a BigTIFF is mandated by this Standard. This provides a clear criteria to discriminate the need for a BigTIFF file that is independent from order and size of the internal parts of the file.

Identifier/req/core/bifh

(The Annex B contains the TIFF version 6 classic structures for comparison purposes).

While the classic TIFF image file header points to the first Image File Directory (IFD), the BigTIFF big image file header points to the first Big Image File Directory (BIFD). In that sense IFD and BIFD are equivalent. Both IFD and BIFD can be located anywhere in the TIFF file. Every ‘page’ in a multi-page TIFF, either classic TIFF or BigTIFF, is represented by exactly one IFD and one BIFD respectively.

Requirement 3

Identifier/req/core/bifd
Included inRequirements class 1: https://www.opengis.net/spec/BigTIFF/1.0/req/core
A

There SHALL be at least ONE big image file directory in a BigTIFF file and each BIFD must have at least one entry

B

A BigTIFF file SHALL NOT contain any classic TIFF image file directory. In other words, BIFD and IFD can not be used together in the same TIFF file.

C

A big image file directory SHALL follow the structure of Big Directory Entries presented in Table 3

D

The big directory entries in a BIFD SHALL be sorted by code (in the same way than classic TIFF requires)

E

Each big directory entry SHALL follow the structure presented in Table 4

F

The tag value SHALL be included inside the tag structure, in the big directory entry, if its size is smaller than or equal to 8 bytes. Otherwise, it SHALL be included elsewhere, and the value SHALL be an offset from the beginning of the file.

G

In case of multibyte values (e.g a SHORT, LONG, etc), the byte order (II or MM) in the TIFF header SHALL govern the order of these bytes.

H

The value of Offset to next BIFD in a BIFD SHALL NOT point to a previous BIFD

I

The type in the BIFD SHALL take priority over the specified (in TIFF Revision 6.0 Final or elsewhere) type of the expected value. In particular, the TIFF Revision 6.0 Final allows for more than one valid type for some fields. For example, ImageWidth and ImageLength are usually specified as having type SHORT, but images with more than 64K rows or columns will use the LONG field type. The type of any specified unsigned integer SHALL be expressed as BYTE, SHORT, LONG or LONG8.

The last item in the requirement allows a single procedure to retrieve any integer value, and makes reading more robust, and saves disk space in some situations.

A BIFD consists of an 8-byte count of the number of directory entries (i.e., the number of fields), followed by a sequence of 20-byte field entries, followed by an 8-byte offset of the next BIFD (or 0 if no other BIFD is required).

Every Big Directory Entry takes up exactly 20 bytes in BigTIFF, and the complete BIFD looks like this:

A TIFF field is a logical entity consisting of TIFF tag and its value. This logical concept is implemented as a Directory Entry in the TIFF version 6 and it is implemented in here as a Big Directory Entry, plus the actual value if it does not fit into the value/offset part, the last 8 bytes of the BIFD Entry.

Table 4 — BigTIFF Tag structure

2uint16Datatype of tag data. See Table 5
4uint64Number of values (n) (it is not the total number of bytes but the number of values)

1 See a list of codes in the TIFF version 6 specification. The GeoTIFF standard adds some extra TIFF tag identifiers.

Each TIFF field has an associated Number of values (n). This means that all fields are actually one-dimensional arrays, even though most fields contain only a single value.

The same rule for value ‘inlining’ the tag data applies to both classic TIFF and BigTIFF, only the threshold size differs. Above the threshold values are pointed by an offset and written elsewhere.

Some good practices inherited from TIFF but not specified in TIFF Revision 6.0 Final are:

  • Number of values (n) cannot be zero.

  • Offset to tag data in multiple tags cannot be shared (e.g. Tag A and Tag B that not point to the same offset).

  • Offset to tag data cannot point to the same fragment of the file (e.g. Tag A points to an area of m bytes, Tag B cannot point to part of the same area).

9.  Media Types for any data encoding(s)

IANA defines the image/tiff media type for TIFF (https://www.iana.org/assignments/media-types/image/tiff). This Standard suggests the use of the same media type for BigTIFF, since it is a superset of TIFF. As a result, the media type image/tiff is used for both Classic TIFF and BigTIFF files. In principle, clients do not need to negotiate with the servers between classic TIFF or BigTIFF. In fact, this kind of negotiation will enter in contradiction with the first recommendation in this Standards that states that servers and writers should only use BigTIFF for files bigger than 4 Gibibytes (232) or when using the data types introduced in BigTIFF. Old clients not supporting BigTIFF will only receive BigTIFF when Classic TIFF will not work for them anyway. Since a modern software is able to programmatically differentiate between a Classic TIFF and a BigTIFF, they can share the same media time for the BigTIFF.

This Standard is also suggesting that same file extension (’tif’ or ‘tiff’) is used for both Classic TIF and BigTIFF, despite other previous proposals such as ‘tf8’ and ‘btf’ (discussed some time ago in the LibTiff mailing list).

Inspect that the BigTIFF begins with a 16 byte big image file header (that replaces the TIFF v6 8 byte image file header). In particular verify that the 2 first bytes correspond to the byte order expected content (0×4949 or 0×4D4D) and the second 2 bytes represent a 42 or a 43. If it is a 42, consider the file as classic TIFF instead of a BigTIFF.


Inspect that the big image file header offset points to an area the content corresponds with a big image file directory (BIFD) structure.

A.1.3.  bifd

Abstract test A.3

Identifier/conf/core/bifd
RequirementRequirement 3: /req/core/bifd
Test purpose

Verify that the section big image file directory exists and is correctly encoded.

Test method

Inspect that there is at least ONE big image file directory in a TIFF file and that each BIFD have at least one entry.


Inspect that a classic image file directory is not present in a TIFF file.


Inspect that a big image file directory follows the structure of Big Directory Entries presented in Table 3.


Inspect that big directory entries in a BIFD are sorted by Tag code (in the same way than classic TIFF does) .


Inspect that each big directory entry follows the structure presented in Table 4. This can be done by examining the Tag codes and the data types and of the TIFF fields and recognize at least some of them (comparing with tables of accepted values).


Inspect that the tag value is written inside the tag structure, in the big directory entry, if its size is smaller than or equal to 8 bytes. Otherwise, inspect that it’s written elsewhere, and pointed to by an offset written as the value.


In case of multibyte values (e.g a SHORT, LONG, etc), Inspect that the byte order (II or MM) in the TIFF header governs the order of the bytes.


Inspect that the value of Offset to next BIFD in a BIFD does not point to a previous BIFD.


Inspect that the type is compatible with the expected value. Since TIFF allows for more than one valid type for some fields, inspect that all types specified as unsigned integer, the type is set to BYTE, SHORT, LONG or LONG8.
